# Limitations of Intrinsics

Using Intel intrinsics is much more convenient than writing assembly code directly. However, this convenience comes at a price: we give up some control over the exact instructions generated by the compiler.

We encounter this limitation when trying to improve pipelining even further.

In this version, we rearrange the intrinsics so that their order resembles the instruction order used in the SSE micro kernel of BLIS. The intention is to schedule independent operations between instructions with data dependencies and thereby hide instruction latency.

However, the compiler is still free to reorder the generated instructions. As a result, the carefully chosen order of the intrinsics is not necessarily preserved at the assembly level.

The benchmarks show that this version does **not** improve performance.

## The `dgemm_nn` Code

The complete implementation is contained in

[`src/level3/dgemm_nn.c`](https://github.com/michael-lehn/ulmBLAS/blob/demo-sse-intrinsics-v3/src/level3/dgemm_nn.c)

on the `demo-sse-intrinsics-v3` branch.

The important part is again the micro kernel.

The comments `(1)` through `(16)` indicate the intended scheduling of loads and arithmetic operations:

```c id="bvihwf"
tmp0 = _mm_load_pd(A);                                      // (1)
tmp1 = _mm_load_pd(A+2);                                    // (2)
tmp2 = _mm_load_pd(B);                                      // (3)

ab_00_11 = _mm_setzero_pd();
ab_20_31 = _mm_setzero_pd();
ab_01_10 = _mm_setzero_pd();
ab_21_30 = _mm_setzero_pd();
ab_02_13 = _mm_setzero_pd();
ab_22_33 = _mm_setzero_pd();
ab_03_12 = _mm_setzero_pd();
ab_23_32 = _mm_setzero_pd();

tmp3 = _mm_setzero_pd();
tmp4 = _mm_setzero_pd();
tmp5 = _mm_setzero_pd();
tmp6 = _mm_setzero_pd();
tmp7 = _mm_setzero_pd();

for (l=0; l<kc; ++l) {
    ab_02_13 = _mm_add_pd(ab_02_13, tmp3);                  // (9)
    tmp3     = _mm_load_pd(B+2);

    ab_22_33 = _mm_add_pd(ab_22_33, tmp6);                  // (10)
    tmp6     = tmp2;

    tmp4     = _mm_shuffle_pd(tmp2, tmp2,
                             _MM_SHUFFLE2(0,1));            // (8)

    tmp2     = _mm_mul_pd(tmp2, tmp0);
    tmp6     = _mm_mul_pd(tmp6, tmp1);

    ab_03_12 = _mm_add_pd(ab_03_12, tmp5);                  // (15)
    ab_23_32 = _mm_add_pd(ab_23_32, tmp7);                  // (16)

    tmp7     = tmp4;
    tmp4     = _mm_mul_pd(tmp4, tmp0);
    tmp7     = _mm_mul_pd(tmp7, tmp1);

    ab_00_11 = _mm_add_pd(ab_00_11, tmp2);                  // (11)

    tmp2     = _mm_load_pd(B+4);                            // (6)

    ab_20_31 = _mm_add_pd(ab_20_31, tmp6);                  // (12)

    tmp6     = tmp3;

    tmp5     = _mm_shuffle_pd(tmp3, tmp3,
                             _MM_SHUFFLE2(0,1));            // (7)

    tmp3     = _mm_mul_pd(tmp3, tmp0);
    tmp6     = _mm_mul_pd(tmp6, tmp1);

    ab_01_10 = _mm_add_pd(ab_01_10, tmp4);                  // (13)
    ab_21_30 = _mm_add_pd(ab_21_30, tmp7);                  // (14)

    tmp7     = tmp5;
    tmp5     = _mm_mul_pd(tmp5, tmp0);

    tmp0     = _mm_load_pd(A+4);                            // (4)

    tmp7     = _mm_mul_pd(tmp7, tmp1);

    tmp1     = _mm_load_pd(A+6);                            // (5)

    A += 4;
    B += 4;
}
```

After the loop, the delayed updates are completed:

```c id="vyqr1e"
ab_02_13 = _mm_add_pd(ab_02_13, tmp3);                      // (9)
ab_22_33 = _mm_add_pd(ab_22_33, tmp6);                      // (10)
ab_03_12 = _mm_add_pd(ab_03_12, tmp5);                      // (15)
ab_23_32 = _mm_add_pd(ab_23_32, tmp7);                      // (16)
```

The important point is that the **source-code order of intrinsics is now deliberately chosen**.

For example, loads for future operands

```c id="08he1v"
tmp2 = _mm_load_pd(B+4);    // (6)
tmp0 = _mm_load_pd(A+4);    // (4)
tmp1 = _mm_load_pd(A+6);    // (5)
```

are interleaved with arithmetic belonging to the current iteration.

At the level of the intrinsic source code, this is close to the schedule we want.

But intrinsics do not prescribe an exact instruction sequence. The compiler can still rearrange these operations when generating assembly.

That is the limitation we run into here.

## What We Learned

Intrinsics give us much more control than ordinary C. We can explicitly choose SIMD instructions, determine how values are grouped into vector registers, and express loads, shuffles, multiplications, and additions directly.

But intrinsics are still **compiler input**.

They do not generally specify the exact order of the machine instructions produced by the compiler.

For most code, that freedom is useful: the compiler can perform instruction scheduling and other transformations for the target processor.

For a tiny performance-critical micro kernel, however, we may want complete control over the instruction stream.

At this point, if we want to determine the exact instruction sequence ourselves, there is one obvious next step:

**write the micro kernel in assembly.**
